title: "Hosted services"
description: "Connect ABX to a compatible hosted resolver."

A resolver indexes ABX events and serves metadata. Run your own or use a compatible provider.

## First-party service

```bash
abx auth login
abx remote abx
abx add 0xYourContract --remote abx
```

`abx auth login` opens a browser flow and saves `ABX_SERVICES_API_KEY` to an ignored `.env`. It does
not print the key. The same sign-in provisions or reuses the creator wallet; an active browser
session can avoid another email code. A later CLI login reuses the loaded key. Creating a key
requires agreement to the [Art Blocks User Terms](https://www.artblocks.io/user-terms.pdf). Existing
keys continue to work; acceptance is checked only when a new key is created.

An account may have five active keys. The service cannot recover a lost key value.

```bash
abx auth keys
abx auth revoke-key <key-id>
abx auth logout
```

The built-in `abx` remote points to `https://services.abx.io`. Other providers can implement the
same interfaces.

To report illegal, infringing, or otherwise prohibited content served by ABX Services, email
[`legal@artblocks.io`](mailto:legal@artblocks.io) with the chain, contract address, exact service URL,
and supporting information. Art Blocks can stop its services from indexing, rendering, or serving a
project; it cannot remove blockchain data or copies held elsewhere.

## Another provider

Add a named remote to `.env`:

```bash
ABX_REMOTE_MYPROVIDER_URL=https://meta.provider.example
ABX_REMOTE_MYPROVIDER_TOKEN=YOUR_API_KEY
```

Then pass the name to any remote command:

```bash
abx remote myprovider
abx add 0xYourContract --remote myprovider
abx status 0xYourContract --remote myprovider --watch
```

A named remote uses only its matching token. It never falls back to another credential.

## What a compatible service exposes

`GET /.well-known/abx-service` returns the provider's chains, interfaces, authentication, rendering,
and contract generations. Its `endpoints` map may place interfaces on different HTTPS origins.
Inspect the descriptor before using a provider:

```bash
abx remote <name-or-url>
```

The first-party catalog, accounts, and project control live at `services.abx.io`. Public token data
lives at `resolver.abx.io`. The CLI follows the descriptor instead of inferring behavior from a
hostname.

The version 1 control plane uses bearer authentication:

| Method and path | Purpose |
| --- | --- |
| `POST /v1/projects` | Register a project. |
| `GET /v1/projects` | List visible projects and status. |
| `DELETE /v1/projects/{chainId}/{address}` | Remove a registration. |
| `POST /v1/projects/{chainId}/{address}/reindex` | Request a fresh index. |
| `GET /v1/projects/{chainId}/{address}/status` | Read progress and freshness. |

Registration may return `202` while indexing continues. `abx add` waits by default. Use `--no-wait`
when another process will watch status. Use `--json` for structured output.

The status words are `queued`, `backfilling`, `live`, `stale`, and `failed`. A stale service keeps
serving its last indexed state.

After the service verifies the factory and core version, project responses include
`contractGeneration`. A missing value means provenance is not established.

## Public reads

Do not guess metadata routes. Read the URI stored by the contract:

```bash
abx tokenuri 0xYourContract --token 0
abx contracturi 0xYourContract --json
```

The public API returns distinct status codes for bad routes, unsupported chains, unregistered
projects, unminted tokens, and burned ERC-721 tokens.

## Leave cleanly

The chain remains the source of truth. Move to another provider or your own resolver with:

```bash
abx migrate 0xYourContract --from <source> --to <destination>
```

The command copies offchain values, checks hashes, and compares both resolvers. It does not update DNS
or the onchain base URI.
