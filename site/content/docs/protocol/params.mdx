title: "Parameters"
description: "Typed, configurable state for code projects."

Parameters are named values on a code project. A program reads them through `tokenData`, and effects
can react when they change.

The contract enumerates and serves its own parameter state. Parameters are not copied into `tokenURI`.

## Scope and values

A contract value is the project-wide default. A token value overrides it for one token.

Scalar values fit in `bytes32`. `String` and `Bytes` values live in an onchain blob; the scalar slot
holds their `keccak256` hash. Each write records the address that made it.

An unset value differs from an empty value. Governed `String` and `Bytes` parameters cannot be written
with zero bytes. Use a sentinel or a companion scalar when the work needs an explicit empty state.

A blob holds at most 24,575 bytes, the most one SSTORE2 data contract can store. Put larger content
behind a pointer parameter. From core v4 the contract refuses an oversized blob before writing it, with
`ParamDataTooLarge(key, length)`; earlier generations fail inside the data-contract deployment instead.

## Schemas

A schema tells wallets and applications how a parameter may be edited.

| Part | Options |
| --- | --- |
| Type | `Bool`, `Select`, `Uint256Range`, `Int256Range`, `DecimalRange`, `HexColor`, `Timestamp`, `String`, `Bytes` |
| Authority | `Creator`, `TokenOwner`, a named `Address`, or supported combinations |
| Constraint | Range bounds or select options |
| Deadline | Optional `lockAfter` timestamp |

On an ERC-721 project, `TokenOwner` accepts full delegate.xyz v2 delegations from the token's owner:
all-wallet, per-contract or per-token delegations made without a rights scope. A delegation scoped to a
specific right does not qualify. On an ERC-1155 edition, `TokenOwner` means any current holder of that
ID, and delegation is not consulted. All holders edit one shared value, not a value attached to each
copy.

The onchain enum is zero-indexed in this exact order:

| Value | Authority |
| ---: | --- |
| 0 | `Creator` |
| 1 | `TokenOwner` |
| 2 | `Address` |
| 3 | `CreatorOrTokenOwner` |
| 4 | `CreatorOrAddress` |
| 5 | `TokenOwnerOrAddress` |
| 6 | `CreatorOrTokenOwnerOrAddress` |

The SDK exports this mapping as `AUTH_OPTIONS`. Decode a `paramSchema()` result with
`AUTH_OPTIONS[Number(schema.auth)]`.

```bash
abx set-schema 0xYourContract \
  --schema 'palette:Select[Ochre|Night|Sage]:TokenOwner'

abx configure-param 0xYourContract 42 palette Ochre --sign
```

Range bounds apply only to `Uint256Range`, `Int256Range`, `DecimalRange` and `Timestamp`. From core v4
the contract refuses a schema that sets `min` or `max` on any other type, because those bounds would be
shown to users but never enforced. It also refuses an empty or malformed-UTF-8 `Select` label, which
would otherwise make every selecting token's metadata undecodable.

A schema may be replaced while it is unlocked. Replacing it does not rewrite or revalidate old values.
The CLI requires `--force` when a change could strand a stored value.

Once a deadline passes, both the value and schema are frozen. A deadline may move earlier, never later.
`retire-param` moves it into the past. Retirement is permanent and keeps the key and old value readable.

An inherited contract default is the exception: the owner can clear it after a schema locks. To make a
value permanent for a token, write it at token scope through the governed path.

## Writes

Scalar and blob types use different contract calls:

```solidity
function configureTokenParam(
    uint256 tokenId,
    bytes32 key,
    bytes32 value
) external;

function configureTokenParamData(
    uint256 tokenId,
    bytes32 key,
    bytes calldata data
) external;
```

Keys are printable ASCII packed into `bytes32`, with only trailing zero padding. Do not hash the key
name. Use the CLI or SDK to avoid encoding mistakes. `seed` is reserved (see below). From core v4 the
tokenData coordinate names `chainId`, `contractAddress` and `tokenId` are refused as keys at every write
path; earlier generations stored them, and renderers ignored them.

`NotParamAuthorized` means the caller did not satisfy the key's current schema; it does not mean
“creator only.” Its shape depends on the generation:

| Generation | Error | What it tells you |
| --- | --- | --- |
| Core v4 | `NotParamAuthorized(bytes32 key, uint256 tokenId, address caller, uint8 auth, address authAddress)` | The key, token and caller, plus the authority that was enforced (`AUTH_OPTIONS[auth]`) and the named address, if any. |
| Core v3 and earlier | `NotParamAuthorized()` | Nothing more. Read `paramSchema(key)`, use `abx state <address>`, or run `abx configure-param` to see the required authority before sending. |

From core v4 the other parameter errors also name the key they concern, so a failing call inside a
`multicall` identifies itself, and every error the parameter library raises is declared in the token's
own ABI. Earlier generations raise most of them without arguments, and their verified token ABIs do not
include them. Decode those against the SDK's `abxCoreV3ErrorsAbi`, which the CLI already includes when
it explains a revert.

First writes cost more than updates because the contract adds the key to its enumeration. Large blob
writes also deploy an SSTORE2 data contract. Keep holder-writable edition parameters small unless shared
large data is the point of the work.

## Enumeration

These reads expose the complete key set:

```solidity
tokenParamKeys(tokenId)
contractParamKeys()
paramSchemaKeys()
```

Paged forms are available for larger projects. Insertion order is not canonical, so consumers should
sort keys before serializing them. The practical design target is about 64 parameters per project.

## Hooks

A code project can set three hooks:

| Hook | When it runs | What it can do |
| --- | --- | --- |
| Configure | Before a governed write persists | Execute contract actions, inspect or reject the new value |
| Augment | During a read | Add or replace computed token data; read-only |
| Transfer | After ownership/balance changes, within mint, transfer, or burn | Execute contract actions, update state or reject the move |

Configure and transfer hooks can call other contracts in the same transaction: for example, a
holder-authorized parameter edit could trigger an AMM swap, or a transfer could create an asset or
settle an obligation. A reverting hook rolls back the operation and its on-chain actions. The hook
needs explicit funding and permissions; it does not automatically gain access to the holder's wallet.
These on-chain callbacks are separate from [off-chain effects](/docs/protocol/effects).

A reverting transfer hook blocks the transfer. Because a mint is a transfer from the zero address, it
can block minting too.

On ERC-721 projects, the hook observes every `Transfer`, including a self-transfer where `from == to`.
That is useful for event-level accounting; a hook concerned only with ownership-set changes can ignore
that case. ERC-1155 projects skip self-transfers and zero-amount entries before calling the hook.

```bash
abx set-param-hooks 0xYourContract --transfer 0xYourHook
abx lock-param-hooks 0xYourContract
```

From core v4 each non-zero hook address must have code when it is set; a codeless transfer hook would
otherwise make every mint and transfer revert with no reason. Re-pointing the augment hook changes every
token's `tokenData`, so it emits ERC-4906 `BatchMetadataUpdate` for the whole collection.

`lock-param-hooks` freezes all three addresses. Freezing an empty set proves that no transfer hook can
be added later. Freezing an active hook leaves it active. There is no permissionless way to remove a
hook after ownership is renounced.

A lock freezes the hook address, not code behind an upgradeable proxy.

## Canonical decode

Programs receive canonical strings in `tokenData`:

- `HexColor` becomes `#rrggbb`.
- `Timestamp` becomes Unix time.
- `DecimalRange` uses ten decimal places.
- `Bytes` becomes base64.
- `String` becomes UTF-8.
- `Select` becomes its option label.

Write a `Bytes` parameter as `0x`-prefixed hex or with `--file`. Base64 is the read form, not the write
form.

## Seeds

`seed` is reserved. The canonical seed source assigns it once at mint. A seed schema allows an
authorized party to choose a replacement value; it does not draw fresh randomness.

The seed schema must exist before any seed is assigned. This lets a buyer inspect whether a seed may
change, who may change it, and when that authority ends. See [Code projects](/docs/protocol/code-projects#seeds).
